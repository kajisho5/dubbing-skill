# Architecture Decision Records

## ADR-001 Engines: Chatterbox Multilingual V3 by default; VOICEVOX, Style-Bert-VITS2 and Kokoro-82M as alternatives

Checked 2026-10-31 against the repositories, model hosts, package indexes and terms pages listed under Sources. Code and weights are judged separately: a permissive code licence says nothing about the checkpoint or the voice a tool uses. AI-video-production-OS ADR-012 named four engines for this skill. Its ecosystem roadmap says candidate engines stay unverified until the owning repository's ADR checks the licences of both code and weights. This ADR is that check. It also looks at the other TTS and voice-conversion engines someone would propose instead.

### Requirements

The skill speaks for conference and event video (talks, panels, interviews), much of it in Japanese or translated into or out of Japanese. The engine has to meet these:

- **Licence.** Code *and* weights allow commercial use of the generated audio. Attribution, credit or a watermark is acceptable if it is recorded. Non-commercial (NC) licences, revenue-capped licences, and weights with no stated licence are rejected.
- **Local and offline.** It runs on the user's machine with no network at run time. Weights are fetched once by the user, never by the skill. An engine that runs as a local app is reached on loopback only.
- **Japanese.** Native Japanese text handling and voices good enough for a narration track. Weak Japanese support is allowed only for a light fallback, and it is labelled as weak.
- **Isolation.** This package stays MIT and stdlib-only. A copyleft engine is never imported. It runs as its own process or app.
- **Obligations are data.** Each engine's credit and watermark obligations go into an `EngineSpec`, then into the provenance of every clip, then into the ProductionReceipt (OS ADR-012).

### Decision

- **Registry.** The engine registry holds exactly the four OS ADR-012 engines: `chatterbox`, `voicevox`, `style_bert_vits2` and `kokoro`. Chatterbox Multilingual V3 is the default for every op. DUB alternatives are the engines that can take a voice per speaker (Chatterbox, Style-Bert-VITS2). NARRATE and AUDIO_DESCRIPTION can also use VOICEVOX and Kokoro.
- **EngineSpec.** Each engine publishes code licence, weights licence, the credit its output must carry (`credit`, `credit_required`), the watermark it embeds, its languages, its Japanese grade (`native` / `weak`), whether it can clone a voice, how it is isolated, its supported version range, its install line, its sources and the date of this check (`licence_checked`). `contract --json` and `engines --json` publish it. Every clip's provenance copies the licence, credit and watermark fields.
- **Isolation.**
  - Chatterbox and Kokoro run in the worker subprocess, preferably under their own interpreter (`DUBBING_CHATTERBOX_PYTHON`, `DUBBING_KOKORO_PYTHON`).
  - VOICEVOX and Style-Bert-VITS2 are apps the user runs. They are reached over HTTP on loopback only (`DUBBING_VOICEVOX_URL`, `DUBBING_SBV2_URL`), and any other host is refused.
  - No engine is a pip extra of this package, and nothing is downloaded by the skill.
- **Availability.** `doctor` reports each engine `OK`, `MISSING` or `INCOMPATIBLE`, with how to install it:
  - Python engines are found by distribution metadata and by the weights file in the Hugging Face cache (or `DUBBING_*_MODEL_DIR`).
  - App engines are found by `GET /version` (VOICEVOX) or `GET /models/info` (Style-Bert-VITS2).
- **Consent.** Voice cloning uses Chatterbox's reference clip or a Style-Bert-VITS2 model trained on a real voice. Either needs a recorded consent of that person (OS ADR-012). Roadmap step 6 enforces this. Until then every op refuses a reference voice before reading it, and so does every engine in the worker (ADR-005).
- **Watermark and credit.** A watermark is never removed or bypassed. A credit is surfaced, never silently dropped.

## ADR-002 Package skeleton: contract, doctor, engine registry and worker before any op

### Context

Roadmap step 1 asks for the skeleton, the contract and doctor, and an engine registry whose `EngineSpec` carries licence, credit and watermark. It is done when doctor lists all four engines with their install status. The pattern is voice-enhance-skill ADR-002, which is modelled on transcription-skill.

### Decision

- **Stdlib-only core, Python >= 3.9.** `pip install dubbing-skill` installs no third-party package. Engines are separate environments or apps (ADR-001), not extras.
- **CLI.** `dubbing contract --json` (alias `skill --json`), `dubbing doctor --json [--offline] [--ffmpeg-skill DIR]`, `dubbing engines --json [--offline]`. With `--json`, stdout holds exactly one JSON document, on success and on failure.
- **Contract in the OS registry shape.**
  - Registry fields: `skill_id`, `version`, `contract_version`, `provides`, `dependencies` with `version_range`, `not_provided`.
  - Also published: `inputs` (the cue list, with translation as a caller input, ADR-003), `tools`, `engines`, `policy` (consent, credit, watermark), `provenance`, `execution` and `errors`.
  - The three ops are published as `provides` with lifecycle `PROPOSED`, and their tools as `implemented: false`: `speech.narrate` (step 2), `speech.dub` (step 5) and `speech.audio_description` (step 7). Each op moves to `EXPERIMENTAL` in the PR that implements it.
- **Typed errors.** One `DubbingError` with a code from a fixed table. The code decides the exit code and the `retryable` flag. Retryable codes: `TOOL_ERROR`, `ENGINE_TIMEOUT`, `CANCELLED`. A declared but unbuilt path raises `NOT_IMPLEMENTED` (exit 5).
- **Engine registry and worker.**
  - Engines are classes with an `EngineSpec`, registered in `engines/__init__.py`. Only registered ids can run.
  - `python -m dubbing_skill.engines.worker <request.json> <result.json>` runs one engine in a child process in its own process group. It has a fixed argv, a minimal environment (`DUBBING_*`, `HF_HOME` / `HF_HUB_CACHE`, no tokens) and the Hugging Face libraries forced offline. Errors come back as structured JSON. `run_engine` kills the whole group on timeout.
  - For Chatterbox and Kokoro the worker starts under the engine's own interpreter when one is configured. This package's import root goes first on `PYTHONPATH`.
  - `Engine.process` checks the op and the availability, then raises `NOT_IMPLEMENTED` with the roadmap step that implements synthesis.
- **Lookups never import an engine.** Python engines are found by distribution metadata (`engines/pkgprobe.py`, a standalone script run with `-I` under the engine's interpreter) and by the weights file in the Hugging Face cache. App engines are found by one GET on loopback (`engines/lookup.py`, the only module that does HTTP). Non-loopback URLs are refused before any connection.
- **`--offline`.** No registered engine needs the network, and loopback is not network. `--offline` changes nothing today. It is accepted and reported so the agent can pass it unconditionally.
- **ffmpeg-skill by capability detection.**
  - The adapter locates a checkout, in this order: `--ffmpeg-skill`, `DUBBING_FFMPEG_SKILL_DIR`, `VIDEO_AGENT_FFMPEG_SKILL_DIR`, `~/.claude/skills/ffmpeg-skill`, `./vendor/ffmpeg-skill`, `../ffmpeg-skill`.
  - It checks every tool and flag the roadmap's wiring needs: `probe`; `join --sample-rate --channels`; `audio --replace --music --duck --audio-stream --overwrite`; `loudness --lufs --measure-only`.
  - It never checks the version number (audio-production-skill ADR-15).
- **Doctor status.**
  - `ok`: ffmpeg-skill is usable and every engine is `OK`.
  - `degraded`: an engine is `MISSING` or `INCOMPATIBLE`. Exit 0, because the skill itself works.
  - `fail`: Python or ffmpeg-skill is not usable. Exit 1.
  - Doctor always lists all four engines, with licence, credit, watermark and install line, and reports translation as `CALLER_SUPPLIED`.

## ADR-003 Translation is a caller input; this skill picks no translation engine

### Context

Dubbing needs text in the target language. The OS ecosystem roadmap (decided 2026-10-30) gives subtitle translation (字幕翻訳) to subtitle-skill, with its MT engine to be chosen in an ADR there. That engine has not been chosen.

### Decision

- **The skill does not translate.** Every op takes cues whose `text` is already in `lang`. Who translated it is the caller's business: subtitle-skill once it has an engine, a human translator, or the agent.
- **No engine is chosen here.**
  - No MT engine is registered, imported, named as a default or listed as a dependency.
  - The contract publishes `inputs.translation` as `{"status": "CALLER_SUPPLIED", "engine": null}`, and doctor reports the same.
  - A unit test fails if the source names an MT engine.
- **Recorded, not produced.** The caller may describe the translation (engine, reviewer) with `--translation-note`. The note goes into each clip's provenance under `translation`. Without a note, the provenance records `{"provided_by": "caller", "engine": null}`.
- **When subtitle-skill decides.** Nothing here changes except the agent's plan: subtitle-skill's translated cues become this skill's input.

## ADR-004 The CLI's JSON is ASCII out, independent of the console code page

### Context

The EngineSpecs carry Japanese text (the VOICEVOX credit `VOICEVOX:ずんだもん`). Windows consoles and pipes encode stdio through a legacy code page (cp1252), so `contract --json` crashed with `UnicodeEncodeError`. A consumer that reads the output with the platform default encoding also failed (`UnicodeDecodeError` in the Windows CI check of `doctor.json`). audio-production-skill hit the same problem and settled it in its ADR-20.

### Decision

- Every JSON document is written with `ensure_ascii=True`: non-ASCII text appears as `\u` escapes. Any consumer on any code page parses the same document, and the decoded strings are unchanged.
- Human-readable output (no `--json`) uses `errors="backslashreplace"` on stdout and stderr, so a console that cannot show Japanese prints escapes instead of crashing.
- A unit test runs the CLI with `PYTHONIOENCODING=cp1252` and checks that the JSON is pure ASCII and still holds the Japanese credit. The CI steps also open `doctor.json` explicitly as UTF-8.

## ADR-005 NARRATE: Chatterbox in the worker, clips laid out by ffmpeg-skill, timed cues blocked on ffmpeg-skill/pad

### Context

Roadmap step 2: text or cues -> clips -> timeline WAV, done when the duration is within tolerance and the receipt records the engine and the watermark. The op follows voice-enhance-skill's frame (`ops.py`): every check before any work, the engine in the worker subprocess, the result validated through ffmpeg-skill/probe, and a rename into place from a private run directory. Every media step goes through ffmpeg-skill (ADR-002). Checked against ffmpeg-skill 2.23.0 (main, 2026-10-31) and the `chatterbox-tts` 0.1.7 wheel from PyPI.

### Findings

- **chatterbox-tts 0.1.7 loads the V2 checkpoint.** Its `mtl_tts.py` (`from_pretrained`, `from_local`) loads `t3_mtl23ls_v2.safetensors`, plus `ve.pt`, `s3gen.pt`, `grapheme_mtl_merged_expanded_v1.json`, `conds.pt` (the built-in voice) and `Cangjie5_TC.json`. `t3_mtl23ls_v3.safetensors` is in the Hugging Face repository (revision `5bb1f6ee`), but no released package loads it. ADR-002's lookup checked for the V3 file only, so it could report OK for a cache that 0.1.7 cannot load, and MISSING for one it can. The lookup now requires all six files in one snapshot (or in `DUBBING_CHATTERBOX_MODEL_DIR`), and the install line fetches exactly those (about 3.2 GB) instead of the whole repository (about 12 GB). The provenance records the file that was loaded.
- **Without pykakasi, Chatterbox skips Japanese normalisation with only a log warning.** The lookup now requires the `pykakasi` module next to `chatterbox` (it is a pinned dependency, so it is missing only from a broken install).
- **ffmpeg-skill 2.23.0 cannot place a clip at a time on an audio-only timeline.** `pad` refuses an input without video ("input has no video stream") and declares `audio_only: false`. No other tool makes silence of a given length or mixes a clip in at an offset: `join` only butt-joins or crossfades, `audio --replace` pads to the length of a *video*, and `fit`, `loop` and `insert` need video.

### Decision

- **Script.** One file: cues (`.json` list or `{"cues": [...]}`, `.srt`, `.vtt`) or plain text (`.txt`, one utterance per non-empty line). The text is already in `--lang` (ADR-003). Limits: 2000 lines, 500 characters per line (Chatterbox stops at 1000 speech tokens, about 40 s), 8 MB. Cues must be in order and must not overlap. Every check runs before the engine starts.
- **Engine run.** All lines go to one worker call (`requests`, results in the same order), so the model is loaded once. Chatterbox runs under `DUBBING_CHATTERBOX_PYTHON` when it is set (ADR-001). Its code is loaded with `importlib` inside `process_batch` only after a check that the process is the worker (`DUBBING_IN_WORKER`, set by the worker itself). It is never imported in the calling process, and a test checks that `chatterbox` never appears in `sys.modules` there. The model loads with `from_local` from the cached snapshot, with the Hugging Face libraries forced offline. Each line is generated with `torch.manual_seed(--seed)` (default 0, recorded) and Chatterbox's default `exaggeration` 0.5, `cfg_weight` 0.5 and `temperature` 0.8. The device is CUDA when available, else CPU (`DUBBING_CHATTERBOX_DEVICE` overrides). The clip is written as 16-bit PCM mono at the model's rate (24 kHz).
- **Watermark.** `generate` embeds the Perth watermark. The worker reads it back from every clip with the model's own watermarker (`get_watermark`). A clip where the mark is not found is refused (`INVALID_RESULT`). If the check itself cannot run, the clip is recorded with `detected: null`, never as passed. The op's `obligations.watermark` and its provenance count the clips where the mark was found.
- **Consent gate.** A reference voice is cloning (ADR-001). Until step 6 can verify a consent record, NARRATE refuses `--reference` and `--consent` with `NOT_IMPLEMENTED` (`roadmap_step: 6`, `reference_read: false`), before any file is opened. `Engine.check_request` refuses `reference_audio` in every engine, in the op and again in the worker. Chatterbox accepts only its built-in voice (`--voice default` or none).
- **Layout, plain text.** The clips are butt-joined in order: `ffmpeg-skill/join <clips> --transition none --sample-rate R --channels 1`, where R is the first clip's rate. One clip needs no join. The expected length is the sum of the clip lengths from ffmpeg-skill/probe.
- **Layout, cues.**
  - Each clip starts at its cue. `ffmpeg-skill/pad --start <gap> --end <tail>` adds the silence before it, and after the last one up to the last cue's end. Then the segments are butt-joined as above. The timeline lasts to the later of the last clip's end and the last cue's end.
  - A clip still playing when the next cue starts is an overflow. With `--on-overflow fail` (the default) the op fails with the new code `TIMING_OVERFLOW` (exit 4, not retryable), and the error lists every overflow. With `shift`, the next clip waits and the drift is reported.
  - A clip longer than its own cue that still ends in time is an overrun. It is reported as a warning, not refused. Fitting lines to their windows (tempo, padding) is step 4.
- **The ffmpeg-skill gap is refused, not worked around.** `pad` is an *optional* tool (`OPTIONAL_TOOLS`), used only when the checkout declares it `audio_only` with `input`, `output`, `start`, `end` and `json`. Against ffmpeg-skill 2.23.0, a cue script is refused with `FFMPEG_SKILL_UNAVAILABLE` before the engine runs. The details name the missing capability, the ffmpeg-skill version and this ADR. Plain text works. `doctor` reports `operations.narrate.inputs.cues.ready: false` with the reason and a warning, without failing (the skill is still usable).
  - An integration test checks that pad's declaration matches its behaviour. When ffmpeg-skill's pad takes audio and says so, timed cues work here with no code change, and the same tests then exercise them.
  - Rejected: writing the silence with Python's `wave` module (a media step outside ffmpeg-skill, against ADR-002 and the README); asking the engine to pad its clips (the same thing, in the worker); and building silence from `audio --gain` plus `join` plus `cut` (many calls, approximate, and not what those tools are for).
- **Validation and placement.**
  - Every clip goes through ffmpeg-skill/probe: readable, with audio, at least 50 ms, else `INVALID_RESULT` naming the line.
  - The timeline goes through ffmpeg-skill/probe: R Hz, mono, and as long as the layout says within max(0.1 s, 1 %). This is the roadmap's "duration within tolerance".
  - The timeline is renamed into place from `.dubbing-*` in the output's directory. The clips are not kept.
  - `join` gained `transition` in `FLAGS_USED`, because capability detection must cover every flag that is used.
- **Receipt.** The result carries a provenance block per clip and one for the timeline. Each block holds the engine id, version, model file, code and weights licences, credit, the declared watermark, the watermark read back, the text hash, the seed and parameters, the translation note and the ffmpeg-skill version. The timeline block also holds the clips' hashes. `obligations` repeats the credit (none for Chatterbox) and the watermark summary for the publisher.
- **Lifecycle.** `speech.narrate` moves to `EXPERIMENTAL` (ADR-002). ADR-001 asked for a Japanese measurement before that. The `engines` CI job runs the real engine on a Japanese and an English fixture: duration within tolerance, the watermark on every clip, and clip lengths plausible for speech. The transcription-skill round trip is not done yet, so NARRATE stays `EXPERIMENTAL`, not `STABLE`.
- **Real-engine CI (`engines` job, Linux).** It is feasible and runs on every pull request, like voice-enhance-skill's `engines` job.
  - It creates a separate venv, installs CPU PyTorch 2.6.0 from the PyTorch CPU index, then `chatterbox-tts==0.1.7`. pykakasi lives only in that venv.
  - It fetches the six checkpoint files at the pinned revision `5bb1f6ee58e50c3b8d408bc82a6d3740c2db6e18`. The four LFS files are checked against the SHA-256 that Hugging Face publishes. The skill never downloads.
  - Doctor must report Chatterbox OK and NARRATE ready for text. Every test must run, including `test_real_chatterbox_narrates_japanese` and `..._english`. The measured durations go into the job summary.
  - Not covered: macOS, Windows and GPU (the unit jobs cover those with the fake engine), and speech quality.
- **Tests without the engine.** A fake `chatterbox` package with a stub `torch` and `pykakasi`, plus a 0.1.7 dist-info, sits on `PYTHONPATH`. The real worker and the real engine code load it exactly as they would load the real one (voice-enhance-skill ADR-004 did the same for nara_wpe). It makes a tone or silence of 0.3 s + 0.06 s per character at 24 kHz and reads the watermark back as present, absent or unreadable. The unit tests use a WAV-only stand-in for ffmpeg-skill (`WaveSkill`, tests only), so the cue layout is tested without FFmpeg. The integration job runs the same op through the real ffmpeg-skill.

### Follow-ups

- ffmpeg-skill: `pad` on audio-only input (its graph already has `adelay` and `apad`), declared `audio_only: true`. Alternatively a join that takes gaps or start times. Timed cues need no code change here once either exists.
- Round trip through transcription-skill on the Japanese fixture (ADR-001) before NARRATE is called stable.
- Chatterbox V3 (`t3_mtl23ls_v3.safetensors`): adopt it when a released `chatterbox-tts` loads it. Then the version range, `MODEL_FILES` and the CI pins move together.
- Step 4 (timing fit) plans the fitting (`dubbing fit`, ADR-007). NARRATE applies it once ffmpeg-skill can change tempo and pad on audio-only input; until then its overrun warning points at `dubbing fit`. Step 6 (consent) replaces the `NOT_IMPLEMENTED` refusal of `--reference`.

### Decision

- **Engine.** `voicevox` synthesises in the worker, one line at a time: `POST /audio_query?text=<line>&speaker=<id>` (no body), then `POST /synthesis?speaker=<id>` with the returned AudioQuery as `application/json`. `outputStereo` is set to false. Nothing else in the query is changed. Defaults: speedScale 1, pre/post 0.1 s. The parameters are recorded. The answer must be a RIFF/WAVE file, mono, at the query's `outputSamplingRate`, with frames, else `INVALID_RESULT`. It is written as `<clip>.part` and renamed into place. An HTTP error from the app is `ENGINE_FAILED` with the status and the app's `detail`. VOICEVOX takes no seed, so the clip's provenance records `seed: null`.
- **Loopback only.** All HTTP is in `engines/lookup.py` (`loopback_request`, used by `loopback_get_json`). The host must be `127.0.0.1`, `localhost` or `::1` over `http://`, and it is checked before a connection object is created. Any other URL raises before connecting: the op reports `INCOMPATIBLE`, a call reports `ENGINE_UNAVAILABLE`. Answers are size-capped (8 MB JSON, 64 MB WAV), and an oversized answer is an error, not a truncation. No proxy is used. http.client does not read proxy variables, and the worker's environment does not carry them.
- **Voice.** `--voice` is a style id, the API's `speaker`, an integer. The default is 3, ずんだもん ノーマル. It is resolved through `GET /speakers` (once per engine instance) to its character, uuid and style. An unknown id, or a style that cannot talk (`sing`, `singing_teacher`, `frame_decode`), is refused with `INVALID_ARGUMENT`, before any synthesis.
- **Terms gate.** A character is verified only when both its `speaker_uuid` and its `name` match the table above. Otherwise the op refuses with the new code `TERMS_UNVERIFIED` (exit 2, not retryable), in the caller's checks before any media work, and again in the worker. The refusal names the character, the style, the derived credit and how to acknowledge. The caller can acknowledge with `--accept-unverified-voice-terms` (`NarrateRequest.accept_unverified_terms`). The credit is then `VOICEVOX:<name>` with `terms_verified: false` and `acknowledged_unverified: true`, and the op adds a warning.
- **Credit in the receipt.** Each clip's provenance gains `credits`: `[{credit, character, speaker, speaker_uuid, style, style_type, speaker_version, terms_verified, terms, conditions, checked_in, acknowledged_unverified}]`. The timeline's provenance and the op's `obligations.credits` hold each distinct credit once, and `obligations.credit` holds their strings (`["VOICEVOX:ずんだもん"]`). For an engine with no per-voice credit, `credits` is the engine's declared credit, or `[]`. Chatterbox's receipt is unchanged apart from the empty `credits`.
- **Contract.** `policy.voice_terms.voicevox` publishes the verified characters (uuid, credit, terms, conditions), the default voice and the unverified rule. The narrate tool lists `--accept-unverified-voice-terms` and the refusal. `provenance.fields` gains `credits`.
- **Version range** stays `>=0.14.0 <1.0.0`. Every field used is present in 0.14.0 and 0.26.0.
- **Absent app.** Doctor reports `MISSING` with the Docker line, as before. NARRATE with `--engine voicevox` is refused with `ENGINE_UNAVAILABLE` before any work. The real-engine tests skip.

## ADR-007 Timing fit: measure each clip against its cue window, plan tempo and silence, report what cannot fit

### Context

Roadmap step 4: fit each line into its cue window (tempo limit, pad, overflow report), done when unit tests cover overflow and underflow. NARRATE (ADR-005) only reports an overrun, and DUB (step 5) needs every translated line to fit its source segment. Translation stays a caller input (ADR-003): the lines are already spoken, by NARRATE or any engine, and this step decides how each clip fits. Checked against ffmpeg-skill 2.23.1 (main, 2026-10-31).

### Findings

- **ffmpeg-skill has no audio-only tempo change.** `fit --method speed` and `speedramp` change tempo with an `atempo` chain, but both declare `audio_only: false`, and `fit` refuses a WAV with `INPUT_INVALID`. `pad` still needs a video stream (ADR-005). `cut` is audio-only, but it trims, and a line is never trimmed here. So a fit plan can be measured and decided today, but not rendered.
- **Measurement is available.** `ffmpeg-skill/probe` reads every clip's duration and audio stream. That is the only measurement used.

### Decision

- **A planning tool, not a media op.** `dubbing fit <cues> <clip>... --json` (`timing.py`, tool `dubbing/fit`, role `analysis`, schema `dubbing/fit@1`) takes cues (`.json`, `.srt`, `.vtt`; plain text has no window and is refused) and one clip per cue, in cue order. It measures every clip through ffmpeg-skill/probe and returns a plan. It writes no media and is deterministic: the same cues and clips give the same plan. The decisions are pure functions (`fit_line`, `fit_lines`) and are unit-tested without FFmpeg.
- **Windows.** A line's slot is its cue, `end - start`. Its room is the slot plus up to `--max-overrun` seconds (default 0, at most 5) past the cue end, never past the next cue's start.
- **Per line, in this order:**
  - `fit`: measured <= slot (within 1 ms). Spoken at tempo 1.0, and the rest of the slot is `slack`, silence.
  - `tempo`: the smallest speed-up that ends the line inside its slot, at most `--max-tempo` (default 1.25, accepted range 1.0 to 2.0). The tempo is rounded **up** to 1/1000, so the fitted length never exceeds the window.
  - Only when even `--max-tempo` cannot end the line inside its slot is the room used, with the smallest tempo that ends inside it (tempo 1.0 counts as `fit`). The overrun past the cue end is reported per line and in the warnings. Speed-up comes first because staying inside the cue keeps the line on its picture.
  - `unfit`: nothing within the limits works. The reason is one of `over_limit` (measured / max tempo > room), `empty_slot` (no room: a zero-length cue, or the next cue starts at or before this one), `empty_clip` (shorter than 50 ms, as NARRATE's clip check) or `not_measured`. The plan gives the tempo it would need and the seconds it is over at the maximum tempo. An unfit line is never cut, never sped up past the limit and never placed. A line is never said to fit without a measurement.
- **Never slowed down.** A short line keeps its tempo and is followed by silence. Slowing speech to fill a slot sounds wrong and changes nothing for sync.
- **Silence.** Placed lines start at their cue's start. `lead` is the silence before each one (from the previous placed line's end), and `tail` is the silence after the last one up to the last cue's end. These are the `--start` / `--end` values ffmpeg-skill/pad would get, so the plan has the same shape as NARRATE's timeline plan.
- **Unfit policy.** With `--on-unfit fail` (the default), any unfit line fails with `TIMING_OVERFLOW` (exit 4), and the error details carry `unfit` and the whole plan. With `--on-unfit report`, the plan is returned (`summary.all_fit: false`, the line indexes in a warning). NARRATE's `--on-overflow fail` follows the same pattern.
- **Checks before measuring.** The limits, the policy, the timeout, the cues, the clip count (one per cue) and that each clip is a file are all checked before ffmpeg-skill is located. A clip ffmpeg-skill cannot read, or one with no audio stream, is `UNSUPPORTED_MEDIA` naming the clip.
- **Rendering waits on ffmpeg-skill.** The plan carries `render: {done: false, reason, needs}`. NARRATE does not apply tempo, and its overrun warning now points at `dubbing fit`. ffmpeg-skill is finished and is not changed from here.
- **Rejected:**
  - Applying tempo with Python (resampling or WSOLA in the `wave` module). That is a media step outside ffmpeg-skill (ADR-002), and resampling changes pitch.
  - VOICEVOX `speedScale` re-synthesis. It is engine-specific, Chatterbox has no equivalent, and it belongs in DUB once a plan exists.
  - Trimming a clip's leading or trailing silence. It needs a silence measurement through ffmpeg-skill. Today the clip is measured whole, which errs on the side of reporting a line as too long.

### Tests

`tests/test_timing.py`, 31 tests:

- Unit, no FFmpeg:
  - Exact fit, and within 1 ms.
  - Padding a short line, never slowing it.
  - Speed-up within the limit, the tempo rounded up, and exactly at the limit.
  - Over the limit reported with the needed tempo and the excess.
  - Overrun room used only when the slot cannot hold the line, and never past the next cue.
  - `--max-tempo 1.0`, zero-length and negative-room slots, empty and unmeasured clips.
  - Lead, slack and tail; unfit lines left out of the layout.
  - 2000 lines; limit and count checks; plain text refused.
- The op on WaveSkill, with non-ASCII directory and file names and Japanese cue text (UTF-8 everywhere, Windows included): the policy, SRT cues, every check before any measurement, an unreadable clip, CLI refusals and the contract entry.
- Integration (CI's integration job): WAVs written by the test, measured through the real ffmpeg-skill/probe, through the op and through the CLI (`TIMING_OVERFLOW` by default, all fitting with `--max-tempo 2`).

### Follow-ups

- ffmpeg-skill: an audio-only tempo change (`atempo`, declared `audio_only`) and audio-only `pad` (ADR-005). Once both exist, NARRATE and DUB render the plan with no change to the decisions.
- DUB (step 5) consumes the plan per translated line.
- Measure the speech inside each clip (leading and trailing silence) through ffmpeg-skill, so a padded TTS clip is not counted as longer than its speech.

## ADR-008 DUB: translated lines fitted to their source segments, spoken over the programme's own sound, through ffmpeg-skill

### Context

Roadmap step 5: replace the dialogue through ffmpeg-skill `audio --replace`, done when the audio and the picture of the result last as long as each other. The chain the user wants is source subtitles or script, then the translation, then TTS, then the timing fit, then a mix with the original sound (ducked). Translation stays a caller input (ADR-003). The timing fit is ADR-007. Checked against ffmpeg-skill 2.24.0 (main, 2026-10-31).

### Findings

- **The silence NARRATE needs is still missing.** ffmpeg-skill 2.24.0's `pad` still declares `audio_only: false` and refuses an input without video (ADR-005). There is still no audio-only tempo change (ADR-007).
- **DUB does not need silence.** A dubbed programme keeps the programme's own sound between the lines. Every piece of it can be made with tools that declare `audio_only: true`:
  - `audio <video> -o programme.wav --audio-stream N` extracts one audio stream as PCM, at the source's rate and layout.
  - `cut <programme.wav> --start --end --accurate -o piece.wav` cuts a sample-exact piece. Its result reports `precision: sample`.
  - `audio <piece.wav> --music <line.wav> --music-volume V --gain -D -o speech.wav` mixes a line over a piece of the programme. The graph is `volume=-DdB` on the piece, then `amix=duration=first:normalize=0`. The result keeps the piece's length, rate and layout. A 24 kHz mono line over a 48 kHz stereo piece gives 48 kHz stereo.
  - `join <pieces...> --transition none --sample-rate R --channels C` joins the pieces.
  - `audio <video> --replace <new.wav>` stream-copies the picture and pads or trims the sound to its length.
- Each step was run by hand on a 6 s H.264/AAC test video before the code was written. The output's audio and picture both lasted 6.000 s.

### Decision

- **Op.** `dubbing dub <programme> <translated cues> --lang L -o <out>` (`dub.py`, tool `dubbing/dub`, schema `dubbing/dub@1`). `speech.dub` moves to `EXPERIMENTAL`.
  - The output is a video (`.mp4`, `.mov`, `.mkv`: the picture is stream-copied) or the new programme audio alone (`.wav`).
  - Engines: those whose spec serves `dub`, Chatterbox (default) and Style-Bert-VITS2 (synthesis in step 8). VOICEVOX and Kokoro do not dub (ADR-001).
- **Translation (ADR-003).** The cues are already translated, one per source segment, at the source's times.
  - `--source-cues` names the source cues. They must be timed, as many, and start and end within 0.1 s of the translated ones, else `INVALID_ARGUMENT` naming the cue.
  - Each line then records `source_text_sha256` in its provenance. No translation engine is named anywhere.
- **Voices.** `--speaker-voice SPEAKER=VOICE` (repeatable) maps a cue speaker to an engine voice. Other lines use `--voice`, else the engine's default. Every line goes through `Engine.check_request` before any media work. A reference voice is refused until step 6, as in NARRATE (`refuse_reference`, now shared).
- **Checks before work.** Every check runs before the engine starts: numbers and policies, paths (output kind, not an input, not existing unless `--overwrite`), cues, alignment, voices, the engine, ffmpeg-skill, and the programme. For the programme, ffmpeg-skill/probe must show the chosen `--audio-stream`, a video stream for a video output, and every cue starting before its end.
- **Timing fit at tempo 1.0.** Each clip is measured through ffmpeg-skill/probe and fitted with ADR-007's `fit_lines`. The room is the cue plus up to `--max-overrun` seconds (default 0, at most 5), never past the next cue's start or the programme's end. `max_tempo` is 1.0, because ffmpeg-skill cannot change the tempo of audio alone. A line longer than its room is `unfit`.
  - With `--on-unfit fail` (the default), the op fails with `TIMING_OVERFLOW`, and the details carry the unfit lines and the plan. Nothing is rendered.
  - With `keep`, the original dialogue stays for that line. It is listed in `kept_original` and in the warnings.
  - The plan says why tempo is 1.0 (`fit.render`). When ffmpeg-skill gains an audio-only tempo change, the planned tempo can be applied with no change to the decisions.
- **Mix (`mixing.py`, shared with AUDIO_DESCRIPTION).** The programme audio is cut at every placed line's start and end.
  - A piece without a line is kept as it is.
  - A piece under a line becomes the line over that piece, with the piece lowered by `--duck` dB (default 12, 0 to 40) and the line changed by `--voice-gain` dB (default 0, -20 to 20). The programme is lowered for exactly as long as the line lasts. That is the ducking.
  - The pieces are joined at the programme's rate, in mono or stereo. A wider layout is mixed to stereo, with a warning.
  - For a video output, the result replaces the programme's audio. No silence is made, and nothing outside ffmpeg-skill touches a sample.
  - ffmpeg-skill's sidechain `--duck` was considered. It ducks the *music* under the main track, so the line would have to be the main track. The result would then take the line's 24 kHz mono format, and the programme under each line would lose its top octave and its stereo image. A fixed gain over the line's exact span keeps the programme's format.
- **Validation.** The output goes through ffmpeg-skill/probe. It must last as long as the programme within max(0.1 s, 1 %). For a video, its audio must last as long as its picture within the same tolerance. This is the roadmap's "A/V duration match", reported as `output.av_delta`. Matroska keeps no per-stream duration, so the container's duration stands in for both.
- **Receipt.** Each clip has a provenance block (op `dub`, speaker, cue, fit status, source text hash), and so does the output (lines placed, lines kept, duck, voice gain, programme layout). `obligations` holds the credits and the watermark summary of the placed clips. `mix.pieces` lists every piece.
- **ffmpeg-skill tools and flags.** `cut` (`--start --end --accurate`) joins `TOOLS_USED`, and `audio` gains `--music-volume` and `--gain` in `FLAGS_USED`. Capability detection checks them like every other tool and flag. The adapter's methods are `extract_audio`, `cut`, `mix` and `replace_audio`.
- **Rejected.**
  - Building one voice track with silence and mixing it in one call. It needs audio-only `pad` (ADR-005).
  - Making silence by lowering programme audio to nothing. That is not what those tools are for (ADR-005).
  - Re-synthesising lines faster. That is engine-specific (ADR-007).

### Tests

- `tests/test_dub.py`, 20 tests, no FFmpeg.
  - The piece plan.
  - The whole op on a WAV programme, with the fake Chatterbox and WaveSkill (which gained `cut`, `mix` and `extract_audio`). The programme between lines is checked sample for sample. Under a line, each sample is checked to be the programme lowered by `--duck` plus the line.
  - `TIMING_OVERFLOW` by default and `keep`; `--max-overrun` bounded by the next cue and by the programme's end; the source-cue alignment; a voice per speaker.
  - Every refusal is checked to come before the engine runs. An engine failure leaves nothing behind. VOICEVOX is refused. The CLI and the contract entry are covered.
- Integration (CI's integration job): a 6 s H.264/AAC test video made with FFmpeg's `testsrc` and `sine` sources (the fixture only; the skill never runs ffmpeg).
  - DUB into `.mp4`: audio and picture match, and the picture is stream-copied.
  - DUB to `.wav`: the programme between lines is byte-identical to a plain extraction, and differs under a line.
  - The CLI into `.mkv`, with `--on-unfit keep`.

### Follow-ups

- A short fade at each piece boundary, once ffmpeg-skill can fade a piece's start and end without fading the whole mix. Today the programme steps down and up by `--duck` dB at the line's edges.

## ADR-009 Consent gate: a reference voice only with a verified consent record of its owner, no way to skip it

### Context

Roadmap step 6: refuse a reference voice without a consent record. It is done when a security test covers it. OS ADR-012 and ADR-001 require a recorded consent of the person whose voice is cloned. Until now every op refused `--reference` with `NOT_IMPLEMENTED` (ADR-005). Chatterbox clones from a reference clip, passed to `generate(..., audio_prompt_path=...)` (chatterbox `mtl_tts.py`, master, read 2026-10-31). Style-Bert-VITS2 clones by training a model on a voice (step 8).

### Decision

- **The record.** It is a JSON file, schema `dubbing/consent@1` (`consent.py`). The contract publishes it as `policy.consent_record`. The fields:
  - `voice_owner.name`: whose voice it is.
  - `consenter.name` and `consenter.relation`: who consented, with the relation `self`, `legal_guardian` or `authorised_representative`. `self` must name the owner.
  - `granted_at`: ISO 8601 with a UTC offset, and not in the future (5 minutes of clock slack).
  - Optional `expires_at` and `revoked`.
  - `scope`: `ops` (required), and optional `engines`, `languages` and `purpose`.
  - `evidence`: at least one file, such as the signed form or a recording of the consent. Each entry has a path relative to the record and a SHA-256.
  - `reference.sha256`: the SHA-256 of the clip the consent covers.
- **The checks.** Every field is checked. Every problem is collected, and any problem refuses the use.
  - Every evidence file must exist, be non-empty, not be the record itself, and match its hash. An edited form no longer counts.
  - The scope must cover the op, the engine and the output language.
  - The record is checked before the reference clip is read. Then the clip's hash must equal `reference.sha256`. A different clip is refused (`reason: reference_mismatch`).
- **One error code.** `CONSENT_REQUIRED` (exit 2, not retryable) is new. `details.reason` is `no_record`, `record_not_found`, `record_invalid` or `reference_mismatch`. `details.problems` lists every problem, and `details.bypass` says there is none.
  - A record without a reference is `INVALID_ARGUMENT`.
  - An engine that cannot clone (VOICEVOX, Kokoro) refuses a reference with `INVALID_ARGUMENT`, whatever the record says.
- **Where it runs.**
  1. In the op, before anything is read. A reference without `--consent` is refused before the engine is even selected (`voice_request_fields`). DUB does this per speaker and names the speaker.
  2. In the engine's checks (`Engine.check_consent`, called from `check_request`), before any engine work. The result is remembered per engine instance, so one op checks each record and clip once. The reference is then probed through ffmpeg-skill: it must be audio of at least 1 s.
  3. Again in the worker, which is a new engine instance in its own process. A record withdrawn or edited between the op's check and the worker is refused there, before `generate` runs.
- **No bypass.** No CLI option, request field, environment variable or contract setting turns the gate off, and none will be added. A test checks every CLI option and request field name for words like skip, bypass, force, ignore and trust. It also checks that no `DUBBING_*CONSENT*` variable exists in the source.
- **Flags.**
  - NARRATE: `--reference PATH --consent PATH`.
  - DUB: `--reference` / `--consent` for every speaker, and `--speaker-reference SPEAKER=PATH` / `--speaker-consent SPEAKER=PATH` per cue speaker. A speaker with its own reference needs its own record. A `--speaker-consent` without a reference is `INVALID_ARGUMENT`.
  - A line has either the built-in voice or a reference, never both.
- **Receipt.** Each clip's provenance gains `consent`. It holds the record's hash, the owner, the consenter and their relation, `granted_at`, `expires_at`, the scope, each evidence file's name and hash, the clip's hash, and what it was verified for. The output's provenance lists each distinct record once. The evidence's contents are never copied. `provenance.fields` gains `consent`.
- **Not decided here.**
  - Whether the evidence is legally sufficient. That is the user's responsibility. The skill checks that the evidence exists and has not changed.
  - Signing records. A hash ties the record to its files, not to a person.

### Tests

- `tests/test_consent.py`, 24 tests. Each covers one problem: 22 record problems, tampered evidence, another clip, a missing or invalid record, the record checked before the clip is opened, and a record without a reference.
- Engines that cannot clone refuse a reference. Cloning engines need a record.
- The worker passes the reference as `audio_prompt_path` only with a record. The worker refuses a record revoked after the op's check, before `generate`.
- NARRATE and DUB record the consent, and every refusal comes before the engine runs. DUB refusals name the speaker. A reference shorter than 1 s is refused. The output is never the reference.
- No bypass in the CLI options, the request fields, the environment or the contract.
- `tests/test_narrate.py`'s consent tests now expect `CONSENT_REQUIRED` instead of `NOT_IMPLEMENTED`.
- Integration: the reference is probed through the real ffmpeg-skill.

### Follow-ups

- Style-Bert-VITS2 models trained on a real person's voice take the same record (step 8).
- An optional signature over the record (a detached signature checked against a key the user names), if a production needs to know who wrote the record.
